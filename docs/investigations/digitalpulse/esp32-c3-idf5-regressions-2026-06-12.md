# ESP32-C3 IDF5 Regression Notes

Date: 2026-06-12

Outcome update:

- this note records the original regression evidence
- the final target-side `digitalPulse` outcome is summarised in
  [conclusion-2026-07-05.md](/home/simon/MaBecker/ESP32_SGATest/docs/investigations/digitalpulse/conclusion-2026-07-05.md)
- the preserved target-side fix is
  [MaBecker/Espruino#4](https://github.com/MaBecker/Espruino/pull/4)

This note records observed regressions when comparing the newer ESP32-C3
Espruino build running on Espressif IDF 5.x against the earlier reference
bring-up build used on the same harness.

## Firmware Builds Compared

Reference build previously used for harness bring-up:

- `BOARD=ESP32C3_IDF4`
- `VERSION=2v29.3`

New comparison build:

- `BOARD=ESP32C3_IDF5`
- `VERSION=2v28`

## Harness Context

Active board and harness:

- ESP32-C3-DevKitC-02
- harness revision v1.1

The comparison should only be trusted when the harness selector state matches
the block under test.

For the confirmed regression below, the harness was in `C3_BASELINE_GPIO`:

- `SEL_D1` -> loop A output
- `SEL_D2` -> loop A input
- `SEL_D3` -> loop B output
- `SEL_D4` -> loop B input
- `SEL_D0` not on `ONEWIRE_DQ`
- `SEL_D08` open
- `J10` signal shunts open

## Confirmed Regression

### `digitalPulse` Fails While `digitalWrite` Works

Status:

- confirmed on IDF5 build
- not explained by harness wiring

Summary:

- normal `digitalWrite` transitions on `D3` are observed on `D4`
- `setWatch` on `D4` sees those normal transitions
- `digitalPulse(D3, ...)` produces no observed transitions on `D4`

This indicates a firmware-side regression in `digitalPulse` behavior on this
target/build, not a general GPIO or watch failure.

## Evidence

### Baseline GPIO Block On IDF5

Script:

```bash
python3 tools/wiring_tests/esp32_c3/gpio_block1.py --port /dev/ttyUSB0
```

Observed result:

```text
PASS LoopA low got=0 expected=0
PASS LoopA high got=1 expected=1
PASS LoopB low got=0 expected=0
PASS LoopB high got=1 expected=1
LoopA edges [1,0,1]
PASS LoopA edge count count=3
FAIL LoopB pulse/watch count=0
```

Interpretation:

- basic static loopback is good
- `setWatch` is not generally broken
- the failing part is the pulse-generation path

### Dedicated `digitalPulse` Reproducer

Script:

```bash
python3 tools/wiring_tests/esp32_c3/digitalpulse_check.py --port /dev/ttyUSB0
```

Observed result:

```text
Board: ESP32C3_IDF5
Version: 2v28
WRITE_SEEN=2
WRITE_STATES=[1,0]
PULSE_SEEN=0
PULSE_STATES=[]
D4_FINAL=0
```

Interpretation:

- `digitalWrite(D3,1)` then `digitalWrite(D3,0)` is seen correctly on `D4`
- `digitalPulse(D3,1,[20,20,20])` produces no observed pulse on `D4`

This is the clearest current regression signal.

## Non-Regressions / Not Yet Proven Regressions

### Basic GPIO Read/Write

Current status on IDF5:

- appears good in baseline loopback mode

Meaning:

- the build can still drive and read GPIO in the simple static case

### `setWatch` On Ordinary Transitions

Current status on IDF5:

- appears good when transitions are generated by ordinary `digitalWrite`

Meaning:

- the watch mechanism itself is not the primary failing component in the tested
  case

### OneWire

Historical status when this note was first written:

- not usable as a clean regression signal between IDF4 and IDF5 yet

Later cross-target testing with a new minimal external OneWire daughterboard
and an Espruino Pico materially improved the evidence quality. See:

- [docs/investigations/onewire/cross-target-comparison-2026-06-15.md](../onewire/cross-target-comparison-2026-06-15.md)

That note shows the same daughterboard and sensors passing a `50/50` soak on
the Pico while remaining unstable on the ESP32-C3 reference build, which makes
an ESP32-C3-specific issue more plausible than a generic sensor-board fault.

Update 2026-06-17:

- this is no longer an open IDF5 regression on the current local firmware tree
- the ESP32-specific OneWire timing fix has been ported to the IDF5 tree in its
  final localized form
- the flashed bench ESP32-C3 passed:
  - `OneWire.searchDebug()` `20/20`
  - `OneWire.searchDebug()` `50/50`
  - DS18B20 conversion/read soak `20/20`
- both sensors were found every time:
  - `2838498700e8136b`
  - `28253387008562df`
- no reset failures were observed
- no `abortedOn11` events were observed
- after that, the original harness-mounted OneWire path was restored with
  `SEL_D0 -> ONEWIRE_DQ` and also passed:
  - `OneWire.searchDebug()` `20/20`
  - `OneWire.searchDebug()` `50/50`
  - DS18B20 conversion/read soak `20/20`
- harness-mounted ROMs found every time:
  - `2808c68700aa7672`
  - `28b3e08700b65ea9`
- latest harness-mounted DS18B20 soak range on the bench:
  - sensor 0: `23.3750..23.5000 C`
  - sensor 1: `24.3125..24.3750 C`

Implication:

- OneWire should no longer be treated as an active IDF5 regression on this
  bench setup
- the original harness OneWire path should no longer be treated as inherently
  suspect
- `digitalPulse` remains the clearer current IDF5 regression signal

## Recommended Next Comparison Order

For further IDF5 regression checking on this harness:

1. baseline GPIO
2. dedicated `digitalPulse` repro
3. analog/PWM block
4. combined SPI/I2C block
5. OneWire standalone regression rerun as a guard check after relevant
   firmware timing changes
6. OneWire coexistence runs with interrupt-driven features active in parallel:
   - Wi-Fi associated and passing traffic during repeated `OneWire.search()`
     and DS18B20 reads
   - Bluetooth/BLE activity running during repeated `OneWire.search()` and
     DS18B20 reads
   - UART RX stress during repeated `OneWire` activity
   - watch/timer activity during repeated `OneWire` activity
   - SPI/I2C polling during repeated `OneWire` activity

Reason for the added coexistence block:

- the current fix uses short ESP32 critical sections only inside the OneWire
  implementation
- bench evidence shows that this fixes OneWire reliability
- remaining acceptance work is to prove that the short interrupt-latency spikes
  do not cause unacceptable side effects in parallel features

Serial-port note:

- do not run multiple REPL harness scripts concurrently against `/dev/ttyUSB0`
  because concurrent access can corrupt the REPL session and produce false
  harness-script failures
