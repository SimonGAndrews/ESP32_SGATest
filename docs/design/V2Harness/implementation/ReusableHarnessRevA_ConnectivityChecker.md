# Reusable Harness Rev-A Connectivity Checker

**Status:** Implemented specification and design

**Governing Rev-A baseline:**
[`ReusableHarnessRevA_DesignBaseline.md`](ReusableHarnessRevA_DesignBaseline.md)

**Implementation:**
[`check-connectivity.mjs`](../../../../KICAD/V2/RevA/Espruino_Harness_RevA/verification/check-connectivity.mjs)

## 1. Purpose

The connectivity checker shall prove that the complete Rev-A KiCad schematic
implements its independently reviewed connectivity contracts. It compares a
root-hierarchy KiCad netlist with the YAML contracts and creates tracked,
deterministic evidence only when every assertion passes.

The Rev-A design baseline requires this check as part of circuit-block and
manufacturing-release acceptance. This document specifies the tool used to
perform that check; the baseline defines when its evidence is accepted.

This check prevents an incorrect schematic and its faithfully generated
netlist from becoming self-validating. Contract content comes from the
requirements, data sheets and accepted circuit analysis; it must not be
generated by copying the netlist.

The checker complements rather than replaces KiCad ERC, visual review,
component/package review and later PCB validation.

## 2. Inputs and authority

The tool consumes three kinds of input:

| Input | Role |
|---|---|
| `ReusableHarnessRevA_Connectivity.yaml` | Identifies the contract set and every contract that must run |
| `contracts/*.yaml` | Defines independently reviewed required and forbidden connectivity |
| `generated/Espruino_Harness_RevA_FullHierarchy.net` | Represents the implemented complete KiCad hierarchy |

The human-readable requirements and design baseline remain authoritative for
behaviour, rationale and acceptance. The YAML files contain only the subset
that can be checked mechanically. The netlist is generated evidence, not
design intent.

## 3. Functional requirements

| ID | Requirement |
|---|---|
| CC-F01 | Load schema-version 1 manifest and contract files and reject unsupported or malformed input. |
| CC-F02 | Run every contract listed in the manifest in one invocation and verify that each manifest ID matches its contract `block_id`. |
| CC-F03 | Parse the complete KiCad s-expression netlist and build component, value, footprint, net and pin membership records. |
| CC-F04 | Check every `pin_net` assertion. A hierarchical KiCad net may match the contract's final net name, but all endpoints declaring the same expected net within a contract must resolve to one actual electrical net. |
| CC-F05 | Check every `component_value` assertion using the exact schematic value. |
| CC-F06 | Check every `forbidden_same_net` assertion and fail if any listed endpoints share an actual electrical net. Missing components, pins or nets are failures rather than ignored items. |
| CC-F07 | Report every mismatch found across the complete contract set in one run. |
| CC-F08 | Return success only when every assertion passes. Return a distinct non-zero result for assertion failures and for tool/input errors. |
| CC-F09 | Write accepted baseline JSON only after a complete successful run. A failed run shall not create or overwrite accepted evidence. |
| CC-F10 | Produce a sorted, timestamp-free and checkout-path-free JSON model so identical connectivity and contracts produce byte-identical output. |
| CC-F11 | Record contract-source SHA-256 hashes, per-contract results, normalized components and nets, and a normalized-connectivity SHA-256 hash in the output. |
| CC-F12 | Support default project paths plus explicit `--manifest`, `--netlist` and `--output` overrides. |

## 4. Design approach

The checker is a dependency-free Node.js command-line program. Keeping it
beside the Rev-A verification files makes its defaults unambiguous and avoids
a package-install step on either Windows or Ubuntu.

Its processing stages are:

1. Parse command-line options and resolve default paths relative to the tool.
2. Read the manifest and its listed contracts using the deliberately limited
   YAML schema supported by this project.
3. Parse the KiCad s-expression netlist into component and electrical-net
   indexes.
4. Evaluate pin/net, exact-value and forbidden-net assertions.
5. Stop without touching the accepted output if any assertion fails.
6. Sort and serialize the complete normalized connectivity model when all
   assertions pass.

The YAML reader is intentionally not a general YAML implementation. Contract
authors shall use the existing schema and assertion forms. Adding a new
assertion type requires an explicit checker and specification change.

### 4.1 Net-name handling

KiCad may export a local net such as
`/Power_Control/TARGET_SWITCH_EN`, while the contract records the stable name
`TARGET_SWITCH_EN`. A `pin_net` comparison therefore accepts either the exact
exported name or its final path component.

This convenience does not weaken electrical identity. When two or more
assertions use the same expected net name, their endpoints must map to the
same complete KiCad net. `forbidden_same_net` also compares actual net
identity, not shortened names.

### 4.2 Exit behaviour

| Exit code | Meaning | Baseline output |
|---:|---|---|
| `0` | Every listed contract passed, or help was requested | Written on a successful check |
| `1` | One or more contract assertions failed | Not written or overwritten |
| `2` | Invocation, file, schema or parsing error | Not written or overwritten |

## 5. Verification workflow

```text
Requirements + data sheets + circuit review
                    |
                    v
         Independent YAML contracts
                    |
Saved root KiCad schematic
        |           |
        |           v
        |     Full-hierarchy netlist
        |           |
        v           v
Full-hierarchy ERC  Connectivity checker
        |           |
        +-----+-----+
              v
   Resolve every error or mismatch
              |
              v
 Accepted ERC + deterministic connectivity JSON
              |
              v
 Update block evidence and status in the design baseline
```

A mismatch is not automatically a schematic defect. Review it against the
governing requirements and data sheets to decide whether the schematic or the
independent contract is wrong. Correct the responsible source, regenerate the
complete root evidence and rerun the whole contract set.

### 5.1 Normal invocation

Save and close KiCad, export the complete production netlist and run
full-hierarchy ERC from `Espruino_Harness_RevA.kicad_sch`. Then run from the
repository root:

```powershell
node KICAD/V2/RevA/Espruino_Harness_RevA/verification/check-connectivity.mjs
```

The same command is valid in Bash when `node` is on `PATH`. Use `--help` to
show explicit path overrides.

## 6. Outputs

The console output gives one PASS/FAIL line per contract, assertion counts and
all mismatches. Successful default operation writes:

```text
KICAD/V2/RevA/Espruino_Harness_RevA/verification/baseline/
  Espruino_Harness_RevA_FullHierarchy_Connectivity.json
```

The JSON contains:

- contract-set and project identity
- checker name and format version
- manifest and contract hashes
- per-contract pass results and assertion counts
- sorted component references, values and footprints
- sorted nets and their component-pin members
- a hash of the normalized connectivity model

Raw netlists and working reports remain under ignored `verification/generated/`.
The deterministic JSON is tracked as accepted evidence. The accepted ERC
report is copied separately into `verification/baseline/` after review.

## 7. Scope limits

Passing the checker proves only that the exported implementation satisfies the
recorded connectivity assertions. It does not prove:

- that the contract fully or correctly represents the requirements
- analogue performance, timing or power integrity
- legal electrical pin types, which remain an ERC responsibility
- symbol-to-footprint or package correctness
- PCB placement, routing, Kelvin geometry, thermal design or DFM
- physical Rev-A operation

These remain governed by
[`ReusableHarnessRevA_DesignBaseline.md`](ReusableHarnessRevA_DesignBaseline.md)
and its release checks.

## 8. Implementation acceptance

The initial implementation is accepted when:

1. its syntax check passes
2. the reviewed PC01, PC02 and SYS01 contracts all pass against a compatible
   full-hierarchy netlist
3. repeating the successful run produces byte-identical JSON
4. a known failing netlist returns exit code 1 and leaves existing output
   unchanged

These four checks passed during implementation. Production acceptance still
requires a fresh root netlist and ERC generated from the saved current KiCad
hierarchy.
